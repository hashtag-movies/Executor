# Hashtag V1.8 Gate 1 — Operation Graph Contract

## Goal

Introduce the contract for multi-step Hashtag work without changing the
existing V10/V11/V1.7 execution path.

## New module

`hashtag/operation_graph.py`

It defines:

- `OperationNode`
- `OperationGraph`
- `OperationGraphError`
- `OperationGraphStateError`

The graph stores existing normalized `Operation` objects. It does not create a
second operation type.

## Contract

A graph contains nodes:

```text
OperationGraph
  ├── graph_id
  ├── nodes[]
  │    ├── node_id
  │    ├── operation
  │    ├── depends_on[]
  │    ├── state
  │    ├── result
  │    ├── error
  │    └── metadata
  └── metadata
```

Node states:

```text
pending → ready → running → success
                         └→ failed

pending/ready → skipped
```

A node becomes ready only after all dependencies are `success`.

## Gate 1 boundary

This gate intentionally does **not**:

- execute operations
- route Bodies
- request permissions
- call the verifier
- recover/re-plan
- learn
- add a new server endpoint
- replace `BodyRecoveryPipeline`
- change the Brain's public `plan()` behavior

## Compatibility

Existing V10 actions can be converted through the existing
`Operation.from_action()` compatibility path.

Existing normalized `Operation` objects are preserved losslessly through
`as_dict()` / `from_dict()`.

## Next gate

Gate 2 can add an adapter that turns an existing Brain plan into an
`OperationGraph` while leaving the current single-operation V1.7 execution
pipeline available as the compatibility path.
